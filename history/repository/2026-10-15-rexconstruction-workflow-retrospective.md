## How Website_Lab is intended to work

Website_Lab combines a design laboratory, project fact store and Framer delivery knowledge base. Its intended cycle is:

1. Resolve user scope, source authority and current project owners.
2. For live work, establish the official Framer connection and targeted readback; choose one primary implementation Skill through the dispatcher.
3. Translate applicable direction and component responsibilities into the existing page/request contract. Existing authorization carries forward; recording a contract does not require another approval.
4. Establish the minimum shared system, then finish sections across responsive widths, content, links and necessary interactions.
5. Evaluate the affected Part using evidence appropriate to the claim; fix executable defects within scope.
6. Synchronize current state and continuation, and save/read back the eligible observation before the final response.

The architecture already supports incremental, evidence-based delivery. The REX problem is the inconsistent application of that cycle and the cost of keeping its records coherent, rather than the absence of a detailed checklist.

## Findings

### 1. Shared-system defects were discovered after page expansion

The build workflow already puts shared Buttons, Navbar and Footer before bulk page construction and calls for a representative visual check. The recorded first build was followed by a user request to fix Navbar/Footer component and responsive ownership.

Inference: the workflow allowed page-level progress to outrun proof of the shared system. The records do not establish exactly which initial tool operation caused this.

Proposal: make the first deliverable a working shared shell, one Button family and a representative section in its real page instances. Inspect Desktop/Tablet/Phone ownership and a narrow/wide case before propagating it. This is an agent self-check within existing authorization, not another mandatory user approval. Reserve user input for actual direction decisions.

### 2. Requirement preservation was weaker than requirement recording

U5.2 already asks for a White **variant**. U5.3 repeats that it belongs inside the existing Button, yet consolidation is still unproven in current Status. The U5.2 observation frames this as a later clarification; the saved prompt shows the earlier request was already explicit.

Proposal: for each revision, turn the existing constraint lock into concrete before/after assertions. For the Button: same definition, Red/White appearances, Yellow filler, preserved Label/Link properties and current corner/geometry decisions. Verify both the requested result and requirements that the change could regress. Do not create a parallel rule file or another full contract for each small change.

### 3. Facts were flagged but not reliably excluded from implementation

The initial counter work was held for approved values. Later records report displayed `10+`, `100+` and `5.0/5` while authoritative values remain Missing. Keeping the site unpublished does not satisfy the content rule for the build.

Proposal: resolve each requested metric to an approved value/source before binding it to a visible instance. Continue independent layout/component work while missing values block only the dependent content. Do not invent replacement business claims or silently remove the user's requested feature. Any proposed alternative content needs the applicable user direction.

### 4. Verification repeatedly stopped at the same boundary

Several observations repeat clean diagnostics, screenshots and preview readiness while runtime paths remain unavailable because staging is disabled. The October 14 record later demonstrates one preview click. This does not establish that a complete runtime path was previously available, or that enabling staging is the correct platform solution now.

Proposal: at the start of an interaction Part, use the official task map to establish which required runtime evidence is obtainable. Validate one representative behavior before multiplying states. If blocked, save the exact missing path, continue independent authorized work, and avoid repeating readiness checks as though they could close the runtime gap. Use focused user confirmation only for a path the user actually observes; do not substitute it for untested behavior or bypass the official gate.

### 5. Current records are easier to contradict than to maintain

The nominal ownership model is clear, but REX still contains competing descriptions:

- The page contract says unverified trust claims remain omitted; current Status reports unsupported displayed metrics.
- The page Reviews section says exact text is Missing; PROJECT and U5 record six supplied reviews.
- Older page-contract decisions describe coral/4px-radius Buttons; the active U5 lock specifies Yellow/square treatment.
- PROJECT's hover summary says button/filler radius was retained, while the active request lock says square. The saved follow-ups do not clearly support that summary's claim of a later radius restoration.
- The single U5 Component Requirement Contract now describes the latest arrow replacement, while its request scope still covers Navbar, Buttons, Reviews and Counters. Its table alone cannot prove closure of that broader scope.

Some dated evidence is intentionally retained and should remain. The issue is historical or superseded intent still appearing as an executable current decision, or a narrow latest result appearing to cover a larger contract.

Proposal: keep current decisions in their existing canonical owner; label superseded decisions and link their replacement. Let the page owner hold enduring acceptance criteria, the request owner hold its active decisions and evidence, and Status hold current outcomes/blockers. Preserve prompt text and append-only observations. Give the latest Part an explicit scope/result within the request rather than overwriting the broader contract's meaning. Avoid adding more files for this small project.

### 6. Closeout compliance is not yet reliable

The October 13 repair already added width routing, observation receipts and validator checks. Re-proposing those as new features would miss the present problem.

This audit's strict run reports **21 errors, 0 warnings**, all in the active U5 request contract: **10 missing scoped evidence links, 9 invalid proof-result cells, 1 invalid contract status and 1 invalid verification status**. In particular, `Partial` is valid for implementation progress but not a supported proof/contract verdict in the existing lifecycle. `N/A` also needs its reason. These are record defects, not 21 demonstrated website defects.

Proposal: make the existing closeout an operational completion step: save actual scoped evidence, use the canonical result vocabulary, synchronize affected current fields, validate and read back before claiming the records are complete. A lightweight affected-project check could improve ordinary-task feedback; it should reuse the canonical schema and would require separate implementation/testing. Keep the full strict validator for knowledge changes. A receipt alone cannot establish semantic consistency or detect an external task that never writes any record.

## Proposed next-homepage sequence

| Part | Deliverable | Exit evidence |
|---|---|---|
| A. Establish direction and dependencies | Existing scope/contract, content and asset readiness, current hard constraints, feasible evidence plan | Actual conflicts and dependent blockers isolated; no unnecessary reapproval |
| B. Prove the shared foundation | Reusable Navbar/Footer, one Button family, representative content section | Definition → real instance → responsive override checks; representative visual and available runtime evidence |
| C. Complete static content | Content-led section sequence, images, actual links, responsive layout, semantics and page metadata | Each Part checked before expansion; whole-page composition checked once assembled |
| D. Add requested interactions | One proven filler/selector/slideshow/counter behavior at a time, only where authorized | All state targets read back; relevant runtime path exercised; missing facts remain blocked |
| E. Close the page | Consolidate components, test width extremes and core journeys, reconcile all open work | Scoped preflight with separate implementation, visual and runtime results; launch-only items distinguished from homepage acceptance |

Interaction ownership and runtime feasibility are considered from the start; this sequence delays bulk decoration, not architecture or essential Phone navigation. Changes to user direction still carry through at any stage. A parent-width correction affects the whole width chain and justifies broader responsive verification; a link correction does not justify repeating whole-page screenshots.

## Priorities and evaluation

1. **Repair current record coherence first in a separately authorized repair task:** resolve the 21 schema/link errors without inventing proof; reconcile current versus superseded decisions and narrow versus broad result scope. Preserve historical evidence. This retrospective does not perform those repairs.
2. **Apply existing execution rules consistently:** shared foundation first, one representative implementation before propagation, constraints checked against the proposed change, claim-matched evidence and completed closeout. Add or change instructions only where an actual routing gap is demonstrated.
3. **Address the highest-risk open homepage items during authorized live work:** approved metric values, White Button consolidation, current filler/width behavior and remaining runtime/stress-width proof. Reconnect and read back before deciding the actual Canvas changes.
4. **Evaluate the process on the next meaningful Part:** distinguish new user preferences from corrective requests; count repeated corrections to the same requirement, unsupported claims, unplanned duplicate components, stale current fields, repeated unchanged-state verification and missing closeout writes. These are proposed measures; no historical baseline or time-saving percentage is available.

Success means the user chooses direction and reviews design quality while the agent catches component, source, responsive and recordkeeping defects before delivery. It does not mean eliminating normal creative iteration or weakening verification to obtain a Pass.
