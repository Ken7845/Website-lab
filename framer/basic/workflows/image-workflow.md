# Framer 图片处理与视觉检查

本文档适用于 Framer 网站的素材盘点、选择、跨页面复用、裁切、修复、上传、放置和响应式检查。选择或复用已有 Canvas 图片也必须先进入本工作流；不能因为无需打开本地文件就绕过素材叙事与重复控制。目标是同时保证视觉质量、网页性能、会话稳定性和中断后的可恢复性。

## 0. 最高优先级：视觉预算与停止条件

图片查看不是默认探索方式，而是带预算的验证步骤。第一次视觉调用前必须写出本轮的 `Image Review Plan`：

- 精确素材或节点数量。
- 每张图只需要回答的一个问题。
- 使用联系表、目标节点截图还是交互 Preview。
- 最大尝试次数和失败后的结构降级路径。

硬限制：

- 一个 Part 最多查看一张联系表，或最多三张单图；不能两种额度叠加。
- 同一文件、同一 Framer screenshot URL 或同一视觉状态在一个任务中只查看一次；把 URL、文件名和判断写入恢复记录。
- 单个素材跨本地下载、Framer screenshot、浏览器和视觉工具总共最多尝试两次。两次失败后立即停止视觉链，改做 Fill、Rect、Style、Alt、Effect target 和实例属性审计。
- 禁止形成 `curl → browser → screenshot → curl` 的循环回退。只允许一个明确备用路径。
- 用户已指定文件名时，只处理这些文件；不扫描整个目录寻找“可能更合适”的图。
- Rename、文本、链接、Property 或其他不改变画面的修改不截图。
- 结构工作先完成并落盘，视觉验证可以单独标记 `Blocked`，不得拖住无关工作。

停止条件不是失败，而是保护任务完成度：视觉工具无输出、CDN 两次失败、文件仍为 dataless、单次输出开始膨胀或无法回答原定问题时，立即结束当前图片审阅。

视觉预算限制调用数量，不取消视觉责任。Section screenshot 只能证明该 Section；Page-level 构图、colour rhythm 或跨页面相似性需要一张高效整页截图或一个 Desktop/Phone 编排图。拿不到合同要求的视觉证据时，将 Visual status 标为 `Blocked` 或 `Fix Required`，不能用结构降级证明审美结论。

## 1. 原图保护

- 不直接对多张原尺寸图片调用视觉查看工具。
- 不在同一轮把多张原图写入上下文。
- 不覆盖 `content-library` 原始素材；压缩、切片、清理和生成结果写入独立工作目录。
- AI 修复前保留压缩编辑输入，输出使用版本号。
- 原图是事实来源，不是默认网页输出文件。

### 1.1 预览前先确认文件已真实落地

文件出现在目录中、`stat` 能返回逻辑大小，不代表图片内容已经可读。macOS / iCloud
可能保留带有 `compressed,dataless` 标记的占位文件；解码器、`file`、图片预览工具或批量脚本
一旦读到这种文件，可能长时间没有输出，而不是立即报错。

预览前先做不解码正文的筛查：

```text
1. 列出文件名和逻辑大小。
2. 用 ls -lO@ 或等价方式检查 flags。
3. 对已落地文件用有单文件时间边界的方式读取像素尺寸。
4. 发现 dataless / offline / cloud-only 文件时，停止读取正文。
5. 先在 Finder 中下载原件，或明确跳过并记录 Missing / Blocked。
6. 只有确认已落地且尺寸可读的文件才进入联系表和单图检查。
```

压缩文件大小不能代表视觉工具的实际负担。一个 500KB WebP 仍可能是
`4644 × 3253`、解码后约 15MP 的图像。判断是否可直接查看时同时看：

- 文件是否真实落地。
- 单图像素尺寸。
- 本轮所有图片的总像素量。
- 解码后的内存量，而不只看压缩后的 KB / MB。

Ken Studio 的 7 张 Painting WebP 单文件只有约 0.18–0.67MB，但合计约 70MP，
RGBA 解码体量约 280MB，尚未计算视觉工具和上下文复制开销。它们不应被当作
“小文件”在一轮中逐张直接查看。已验证的安全路径是生成约 `948 × 834`、
74KB 的 JPEG 联系表，并只查看该联系表一次。

禁止在完成这一步前：

- 对整个未知目录直接运行 `file`、图片尺寸探测或批量解码。
- 把未知状态原图直接交给 `view_image` 或其他视觉查看工具。
- 因为工具没有立即报错，就继续等待或重复提交同一批读取。

Ken Studio 2026-07-26 复盘：`images/works/shadow/shadow-8.JPG` 带有
`compressed,dataless` 标记。对包含它的目录执行无边界批量 `file` 读取时持续无输出；
Ken Studio-4 和 Ken Studio-5 也都在进入图片查看阶段后中断。该文件状态是已验证的
阻塞风险；聊天记录本身没有返回明确的 `view_image` 错误，因此不能把唯一根因写成
视觉工具故障。正确结论是：未筛查的素材读取链缺少驻留检查、超时边界和降级路径。

任务记录进一步确认：

- Ken Studio-4 的浏览器截图调用已经成功完成，耗时约 156ms；任务是在之后被标记为
  `interrupted`，没有截图或图片工具错误。
- Ken Studio-5 的最后状态是“评估图片查看方式”，随后被标记为 `interrupted`；
  记录中没有实际 `view_image` 调用，也没有错误返回。
- 两个任务的首轮分别持续约 649s 和 612s。大量规范读取、Framer 连接、画布审阅和
  图片判断堆在同一轮，使图片阶段成为最后可见位置，但不能据此认定它是唯一根因。

因此后续排查必须区分：

```text
工具明确报错
≠ 任务在图片阶段被中断
≠ 云端占位文件导致的无输出读取
≠ 高像素素材造成的解码或上下文压力
```

2026-07-30 进一步复盘：聊天再次停在图片审阅附近，实际浪费来自多条验证链叠加，而不是单一图片工具。已确认的放大因素包括：

- 已经通过文件名或稳定 URL 识别的素材仍被重复下载和查看。
- 全页截图、目标节点截图、浏览器截图和本地原图检查没有预先分工。
- CDN / SSL 临时失败后继续切换工具重试。
- 每次小改动都重新跑接近 Page 级的视觉审查。
- 图片验证与规则阅读、结构修改和最终 QA 被压在同一长轮次。

因此以后先选一条视觉证据链，再按风险等级审查；不得为了“更确定”无限增加证据来源。

在进入第一次视觉查看前向项目 canonical Recovery owner 写一次当前检查点，记录已完成读取、当前 Framer Session、
下一张待查看的已验证预览图和可降级路径。长任务不能把全部资料读取、画布审阅、
多图预览和写入都压在同一轮中。

### 1.2 Framer 画布截图的安全检查路径

画布 QA 与原始素材检查是两条不同链路。检查 Framer 页面、Section 或 Component
Variant 时，优先让 Framer 生成目标节点截图，不把本地原图重新送入视觉工具：

```text
targeted serializeNodes 结构检查
→ readProject screenshot（精确 node id）
→ 取得单张 image_url
→ 仅下载该压缩截图到临时目录
→ 用 node_repl.emitImage 检查
→ 立即回到节点属性与 Rect 审计
```

稳定性要求：

- 每次只截当前需要判断的节点或 Variant；不要用整页大图代替局部检查。
- 优先使用 `readProject` 的 `screenshot` 返回 URL，不输出原始像素 Buffer。
- 禁止把 `framer.screenshot()` 返回的 Buffer 直接 `console.log`；它会产生数万行数字，
  放大上下文和传输压力。
- 临时截图不进入 `content-library`，不覆盖原素材。
- `node_repl.emitImage` 只接收已经生成的小型 PNG/JPEG；不要用它绕过原图驻留筛查。
- 截图 URL 下载失败时，不重复循环提交；回退到 `serializeNodes`、`getRect`、Fill URL、
  Text Style、链接和 Effect target 的结构核对。
- 组件检查按 Variant 分开截图；响应式页面按 Desktop、Tablet、Phone 分开截图。

Ken Studio 2026-07-27 已验证：Footer 三个 Variant 和 Home Creation 节点可通过
Framer on-demand screenshot → 临时 JPEG → `node_repl.emitImage` 完成视觉检查，
全程无需对 Painting 原图调用 `view_image`。

### 1.3 AURELIA 2026-08-04：整页长截图连续进入上下文

AURELIA-1 的中断已通过任务日志复核。它不是素材原图解码失败，也不是 Framer 写入失败：

- Hero 后的 `Vision → Chef → Space → Craft → Experience → Signature → Invitation`
  已成功写入 Desktop、Tablet、Phone，并完成 Navbar 锚点和 Footer 文案调整。
- Framer 已成功生成 Desktop 与 Phone 两张整页 on-demand screenshot。
- 两次本地 `view_image(detail="high")` 都成功返回，没有工具错误；序列化视觉输出分别约
  108,644 和 63,720 个字符。
- 第二张整页图写入上下文后约 5 分钟没有继续产出，任务最终被手动标记为
  `interrupted`。因此不能把结论写成“`view_image` 报错”，准确结论是：同一长轮次
  连续载入两张高细节整页长截图，叠加既有超长上下文，造成视觉推理阶段失去响应。

这类截图压缩后文件可能不大，但页面高度会让总像素量、Base64 传输和视觉上下文显著
膨胀。以后 Framer 页面 QA 增加以下硬限制：

```text
结构回读并写恢复点
→ 只选一个当前最重要的断点
→ 只截一个 Section / Component / 有界页面裁片
→ 控制预览最长边 ≤ 1200px、总像素尽量 ≤ 2MP、文件 ≤ 1MB
→ 单次只调用一次视觉查看
→ 立即把结论覆盖写回 canonical Recovery owner
→ 下一断点放到下一轮或下一视觉 Part
```

- 禁止对 Desktop 和 Phone 两张整页长截图连续调用 `view_image`，无论文件大小。
- 禁止对 Framer 整页长截图使用 `detail="high"` 作为默认最终检查；先缩小并裁成当前
  问题所需的一个有界区域。
- 响应式 QA 先用节点树、Rect、文本换行、Fill、Alt、链接和 Effect 属性批量检查；
  视觉工具只回答结构数据无法回答的一个构图问题。
- 如果必须检查整页节奏，先生成低像素联系表，只检查一个断点；另一个断点改用局部
  Section 截图或放到下一轮。
- 一次视觉输出返回后必须先形成判断并覆盖更新 canonical Recovery，不能立即加载第二张图。
- 对已完成写入的长任务，视觉验证超预算时标记 `Visual QA incomplete` 并正常交接，
  不让已经完成的 Framer 改动因最后一张图而失去任务回复。

## 2. 联系表优先

素材盘点先生成联系表，再查看单图：

- 单张素材最长边不超过 1200px。
- JPEG 质量约 50–60%。
- 单张联系表尽量控制在 1MB 内。
- 每轮最多查看一张联系表。
- 联系表包含序号或短文件名，确保能回到源文件。
- 联系表必须由已确认落地的文件生成；任何 dataless 文件先排除并在标签中标记。
- 视觉工具只查看生成后的小型 JPEG / PNG 联系表，不直接查看未知原图或一组 WebP。

推荐分类：

- Hero / Exterior
- Food / Product
- Atmosphere / Interior
- Menu / Text Source
- Contact / Hours / Map
- Reviews / UI Screenshots
- Reject / Blurry / Duplicate

只有入选素材才进入单图检查、修复和网页输出阶段。

## 3. 四合一、拼图和批量切片

如果一张源图由多张照片拼合：

1. 先读取像素尺寸并确认网格规律。
2. 用脚本一次性批量切片，文件名保持稳定顺序。
3. 生成切片联系表，检查边界、重复、黑边和错位。
4. 只对问题切片单独返工，不逐张手工重复裁切。
5. 上传前生成网页尺寸版本，保留切片源文件用于恢复。

已知规则明确时，应使用一个批处理脚本完成全部切片，不要进行 20 次独立工具调用。

## 4. 网页输出尺寸

- 输出尺寸根据实际容器和设备像素需求决定，不统一使用原始分辨率。
- Hero、全宽图片和 Gallery 放大图保留较大版本；卡片缩略图使用更小版本。
- 优先选择现代网页格式；需兼容时使用合理压缩 JPEG/PNG。
- 上传前记录源文件、网页输出和 Framer 使用位置的对应关系。
- 禁止直接上传明显超出容器需求的超大截图。

### 4.1 用户明确要求 WebP、体积上限与删除旧格式

此流程只在用户明确同时或分别指定 WebP、单文件体积上限、替换范围或删除旧格式时启用；不得把某项目的数值（例如 `500KB`）推广为默认标准。未收到删除授权时，仍遵循 §1 的原图保护规则。

1. 先列出精确目标、检查文件驻留状态，并记录用户给出的格式、字节上限和目录范围；外部源目录与项目素材库必须分别确认。
2. 对每个目标以稳定短文件名生成同名 `.webp` 输出。质量与像素尺寸可逐级降低，但必须保留足以承载该图片叙事职责的清晰度。
3. 每个输出均须通过三项验证后才可视为成功：扩展名为 `.webp`、解码器报告 WebP、文件大小不超过用户上限。任一项失败时保留旧文件并标记失败，不得继续删除。
4. 只有用户明确授权删除时，才在对应 WebP 已完成三项验证后删除同一目标的旧 JPG/PNG；不得删除未在本轮清单中的文件、未验证输出或任何其他项目素材。
5. 替换 Framer 时，盘点并更新所有实际引用：静态 Fill、CMS 图片字段、页面/Root 社交图、favicon、深色 favicon、Apple 图标以及用户明确要求的可见 Logo。随后以 targeted readback 确认这些 URL 已指向 WebP，并保留原有 Alt 文本或更新为真实描述。
6. 在项目 current-state 中记录目标目录、文件数、上限、验证方法、删除授权和仍未替换的引用；不要把过程日志复制为第二份 current state。

已验证的项目级来源：Summit Roofing，2026-08-23。用户要求所有素材转 WebP、每张不超过 `500KB` 并移除旧格式；Desktop 源目录与项目素材库分别完成字节/解码检查，随后对 Framer 静态图、CMS 图和站点图标完成 targeted readback。此处记录的是条件性工作流，不是对其他项目的默认体积或删除规则。

## 5. 裁切第一性原理

裁切判断标准是“核心视觉信息是否完整”，不是机械要求整张图片完整显示。

先识别图片表达对象：

- 菜品主体与关键配菜
- 建筑入口和招牌
- 人物动作
- 空间关系
- 必要文字信息

核心信息仍清晰时，可以使用 cover、局部放大、跨列和横竖比例混排建立节奏。

以下情况不能强行 cover：

- 切断菜品主体。
- 遮掉关键配菜或产品细节。
- 破坏建筑、人物或空间关系。
- 删除必要文字。

此时应调整焦点、容器比例、跨列方式，或更换素材。

“保证内容完整”不等于全部使用同一比例、`contain` 或无裁切展示。Gallery 与首页图片应有节奏，但每次裁切都要能说明保留了什么信息。

### 5.1 图片内容完整性优先于版式便利

排版必须同时尊重图片内容。图片被放入页面前，先明确它承担的叙事信息；容器比例、`cover` 裁切和焦点位置都必须服务该信息，而不能只服务统一网格或视觉整齐。

- 如果裁切使人物、菜品主体、手部动作、空间关系、工具、服务动作或必要文字大量缺失，导致图片已无法读出原有内容，则该图片不应继续使用在该位置。
- 出现上述风险时，依次选择：调整焦点、改用更符合源图的容器比例、让图片按原比例或 `fit-image` 展示、改变跨列或阅读顺序、或更换为信息角色更匹配的素材。
- 不得用固定高度、统一卡片比例或纯粹的构图偏好，强迫重要内容进入不可读的裁切。
- 每个 Desktop、Tablet、Phone 图片位都要重新判断；不能把 Desktop 的裁切和焦点机械继承到窄屏。

### 5.2 跨页面素材选取与重复控制

在为新页面或新 Section 选择图片前，必须先检索当前项目 `content-library/<project>/images/` 的目录、文件名、已有使用位置和对应叙事角色；在符合本文件的驻留检查、视觉预算和联系表规则前提下，筛选最能支持当前段落内容的素材。

- 图片选择先匹配叙事职责，再考虑颜色、比例和装饰性；不得为了快速填充而随意复用已有页面的图片。
- 同一图片可以在确有不同信息角色、且不削弱页面独立叙事时复用；否则优先选择尚未使用、但更贴合当前内容的素材。
- 记录当前页面使用的图片、Alt 和叙事作用；避免在不同页面无意识地反复引用同一张图片。
- 素材检阅仍必须遵守本文件的防卡顿路径：先检查驻留与尺寸，再用限定数量的联系表或目标化单图审阅；不得为“找更多图片”而无边界读取整个图片库。

新 Page 或重大 Section 视觉工作在选图前建立项目级 Asset usage ledger；PROJECT 只记录当前分配和使用事实，不复制本工作流：

| Asset | Narrative qualities | Approved role | Current use | Reuse decision / reason | Crop / focal notes | Status |
|---|---|---|---|---|---|---|

- `Current use` 必须包含已使用的 Page / Section，不能只写 Uploaded。
- 复用 sibling page 图片必须说明它为何承担新的信息角色；“已经上传”或“比较快”不是理由。
- 已分配素材必须是 `Used`、`Reassigned — reason` 或 `Blocked — reason`；不能静默遗漏后继续报告完成。
- Visual Direction Contract 的 Asset map 只编译本轮选中项并链接 PROJECT owner，不复制完整库存。

## 6. 响应式图片检查

Desktop、Tablet、Phone 分别检查：

- Desktop 可使用宽幅、跨列和更复杂构图。
- Tablet 减少跨列复杂度并重新检查焦点。
- Phone 通常改为单列或更简单节奏，重新设置高度与焦点。
- 不把 Desktop 的固定高度和跨列裁切直接复制到 Phone。
- 作品集、摄影与案例封面优先使用原比例与 `fit-image`；统一卡片矩阵才使用固定比例 cover。

## 7. 截图清理与 AI 增强

- Google Maps 发布者信息、黑块、角落按钮、底部控件和截图痕迹必须修复或重新生成，不能只靠裁剪遮挡。
- 模糊图片只在内容重要且没有替代素材时增强。
- 增强后检查建筑、菜品、标识、文字和空间结构是否被 AI 改写。
- AI 输出不能替代事实核验，尤其是菜单、价格、招牌和地址。

## 8. 菜单与文字截图

- 菜单截图作为事实来源，不作为最终主要阅读界面。
- 优先 OCR 或人工校对提取菜名、分类、说明和价格，再用真实文本排版。
- 无法确认的内容不猜测；省略并标记待核验。
- “价格和供应可能变化”的提示不能掩盖错误转录。

## 9. Framer 中的图片结构

图片 hover 推荐：

```text
Image Frame
└── Image Content
```

- 外框负责尺寸、圆角、边框和 `overflow: clip`。
- 内部图片负责轻微 hover scale。
- 不让整个卡片、边框和布局容器一起 scale。

Gallery 简单放大优先使用 Lightbox Effect，不为不同照片创建 20 个 Variant 或 Overlay。相同结构、不同照片使用 Image/Fill Property 或直接替换 Fill。

## 10. Alt Text

每张图片必须明确选择：

- 信息性图片：简短、具体、与上下文相关的 Alt Text。
- 装饰性图片：显式空 Alt。

不能保留未定义状态。Alt 描述图片传递的信息，不堆砌关键词，也不重复紧邻标题。

## 11. 批量任务与 reconnect 防护

Framer 上传、图片生成和大量素材处理拆成可恢复阶段：

```text
素材盘点
→ 批量处理
→ Desktop 放置
→ Tablet 调整
→ Phone 调整
→ Preview / Lightbox 检查
```

每阶段在项目 `RECOVERY.md` 或 PROJECT 的单一 Recovery 章节覆盖记录：

- 项目和页面路径。
- 当前 Framer Session。
- 已处理素材和输出路径。
- 已上传内容。
- 已完成断点。
- 未完成项。

稳定性规则：

- 临时脚本使用明确名称。
- 批处理使用一个可重复脚本，不依赖匿名命令。
- 复用同一 Framer Session，不主动 reconnect。
- 大量原图不在一次调用中同时上传或查看。
- 每次视觉查看只传一个已验证文件；优先传小于 1MB、最长边不超过 1200px 的联系表。
- Framer 画布优先使用精确节点截图；不要打印截图 Buffer，也不要为视觉 QA 重新读取原图。
- 第一次视觉查看前先完成文件 flags、大小和解码可用性检查。
- 未知目录的批量读取必须有单文件边界；一个文件异常时可以跳过，不能拖住整批。
- 工具等待过久后先读取当前状态，不重复提交同一批写入。
- 命令无输出时通过页面树、素材状态或 Preview 回读，不根据命令结束假设成功。
- 接管中断任务时先读最后成功状态，不从头重做。

### 图片预览失败后的固定降级路径

```text
停止继续预览
→ 记录最后成功文件和疑似问题文件
→ 检查 dataless / offline flags
→ 用已落地素材重新生成更小联系表
→ 最多重试一次联系表
→ 仍失败则改用文件名、尺寸、Framer 节点 Fill 和已有截图完成结构审阅
→ 把视觉判断标记为 Blocked，不让整项 Framer 任务一起卡住
```

图片视觉检查是一个可降级子步骤，不是长任务的单点阻塞条件。若结构、文案、Styles、
Breakpoint 或 Layer 命名仍可通过 Framer targeted read 完成，应继续这些只读工作，
不要等待视觉工具恢复后才推进全部任务。
